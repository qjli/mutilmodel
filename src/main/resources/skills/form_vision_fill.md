# form_vision_fill

面向「企业基本信息 / 企业资质 / 专业资质」结构化表单的视觉识别与抽取。

## 何时加载

用户上传营业执照、许可证、资质扫描件等多张图片，需要从影像中回填右侧表单字段时，必须加载本技能并严格按其字段约定输出。

## 字段键（form_patch）

`form_patch` 的键名必须使用 **camelCase**，与前端表单 `name` 一致，例如：

- `companyName`, `companyShortName`, `formerName`
- `enterpriseNature`, `enterpriseType`, `businessScope`
- `companyPhone`, `companyEmail`
- `registrationDate`（ISO-8601 日期字符串，如 `2018-03-15`）
- `registeredRegion`, `registeredAddressDetail`, `actualLocation`, `registeredZip`
- `registeredCapital`（字符串，单位万元，与表单一致）
- `companyFax`, `learnChannel`
- `unifiedSocialCreditCode`, `qualificationIdDocType`, `qualificationIdDocNumber`
- **安全生产 / 危险品经营许可证等**（与表单「危险品经营许可证」区块一致）：
  - `safetyAdminLicenseName`：证照上的行政许可名称 / 证书名称（如「危险化学品经营许可证」）
  - `safetyLicenseNo`：证书编号 / 许可证编号
  - `safetyLicenseValidityMode`：`fixed`（有明确起止日期）或 `long`（载明「长期」「长期有效」等）
  - 当 `fixed` 时：`safetyLicenseValidityRange` 为 **两元素 ISO 日期字符串数组** `[start,end]`（与证面「有效期自/至」「有效期限」一致）
  - `**safetyIssuingAuthority`（发证机构，必填尽量抽取）**：发证机关全称。证面常见标签见下文「发证机构 / 法人代表」小节。
  - `**safetyLegalRepresentative`（法定代表人或负责人，必填尽量抽取）**：证面「法定代表人」「主要负责人」「企业负责人」等；若仅出现「负责人」且无更具体称谓，仍填入本字段。
- **危化品运输许可证**（若影像为该证）：
  - `transportAdminLicenseName`, `transportLicenseNo`, `transportLicenseValidityMode`
  - 当 `fixed` 时：`transportLicenseValidityRange` 为 `[start,end]` 的 ISO 字符串数组
  - `transportIssuingAuthority`、`transportLegalRepresentative`：版式与安全生产类证照类似，按证面同义词抽取。

`**form_patch` 写入原则（与歧义配合）**

- 一般情况下：只输出**有把握**从图片读到的字段；读不清、不确定的不要猜进 `form_patch`。  
- **例外（强制）**：若出现下文「多张证照与同一表单字段」中的**多主体冲突**，对冲突字段**不得以「对其中一家更有把握」为由**写入 `form_patch`；**必须**走 `ambiguities`，`form_patch` 中**省略**这些键（或整段工商基础信息均不写，直至用户确认）。

## 多张证照与同一表单字段（强制歧义）

右侧「企业基本信息」等区块中，多数字段在数据模型上为**单行单值**（例如一个企业只能对应一个 `companyName`、一个 `unifiedSocialCreditCode`）。

当本轮影像中同时出现 **≥2 张营业执照（或同等效力的工商登记照）**，且证面分别记载 **不同经营主体**（企业名称或统一社会信用代码等明显指向两个及以上法人实体）时，凡下列 **camelCase 字段** 在证面之间存在 **互斥的多个明确取值**，一律视为存在歧义：

- `companyName`、`companyShortName`
- `unifiedSocialCreditCode`
- `enterpriseType`、`enterpriseNature`（若两证记载类型不同且均清晰）
- `registeredAddressDetail`、`registeredRegion`、`registeredZip`
- `registrationDate`、`registeredCapital`
- `businessScope`（若两证经营范围文本实质不同、且无法合理合并为一句不损真的摘要）
- 两证均出现的其它**同一键**、**不同值**的工商字段

**必须执行：**

1. 上述每个发生冲突的 `field_key`：**不得**在 `form_patch` 中出现该键（勿任选其一写入）。
2. 在 `ambiguities` 中为每个冲突字段各建一条：
  - `question_for_user`：中性说明原因，例如「上传了多张营业执照，分别对应不同企业名称，无法自动确定应填入表单的唯一主体」。  
  - `options`：**每个候选对应一张证照来源**，`label` 中写清区分依据（如「证照 A（正本）·企业名称：…」「证照 B（副本）·企业名称：…」），`suggested_value` 为选中后写入该 `field_key` 的字符串（与证面一致，勿编造）。  
  - `option_id`：简短唯一即可（如 `lic_a`、`lic_b` 或 `shaanxi`、`henan`）。
3. `reply` 的【待确认 / 歧义】必须与 `ambiguities` **逐条一致**；**禁止**在【已抽取字段】中把两套主体的同一语义字段并列列出却又不给 `ambiguities`（即禁止「叙述上两套、结构上无歧义」）。

**非冲突情形（可不造歧义）**

- 多张图实为**同一企业**的重复角度、同一证正副本信息完全一致。  
- 一张为营业执照、另一张为**许可证**且字段分属不同区块（如 `companyName` 与 `safetyLicenseNo`）无键冲突。

## 危险品经营许可证 / 安全生产类证照：发证机构与法人代表

此类证照（含「危险化学品经营许可证」「安全生产许可证」等变体）上，**发证机构**与**法定代表人/负责人**经常出现在下列位置，须逐项核对，避免漏抽：

1. **版式位置**
  - 正文区中部或偏下：成对出现「发证机关：……」「法定代表人：……」或表格单元格。
  - 右下角或骑缝章附近：红色公章上的单位名称往往就是 **发证机关**；公章旁或编号下方可能有机关打印名称，与公章一致时取**打印全称**（更清晰则优先用打印字）。
  - 页眉、页脚、侧边栏：部分省份模板把「发证机关」放在证书底部横条。
2. **发证机构 → `safetyIssuingAuthority` 的常见字样（等价识别）**
  - 「发证机关」「发证单位」「颁证机关」「许可机关」「审批机关」「发证部门」
  - 「（盖章）」上一行或左侧的行政机关全称（如「××市应急管理局」「××省应急管理厅」）
  - 若证面仅有公章无打印机关名：可据公章环内/章边可辨文字推断；**仍无把握时**不要编造，可放入 `ambiguities` 让用户确认，或留空不写 `form_patch` 该项。
3. **法定代表人 / 负责人 → `safetyLegalRepresentative` 的常见字样**
  - 「法定代表人」「法定负责人」「企业法定代表人」
  - 「主要负责人」「负责人」「企业主要负责人」（危化经营许可证常用「主要负责人」表述，**一律映射到 `safetyLegalRepresentative`**）
  - 勿与「经办人」「领证」混淆；经办人不是法人代表字段。
4. **与其它字段区分**
  - 「企业名称」「经营者名称」「单位名称」对应的是经营主体，**不是** `safetyLegalRepresentative`（除非证面明确写该人即为法定代表人且与姓名行绑定，此时姓名写入 `safetyLegalRepresentative`，企业名称可对应 `companyName` 等若你也识别营业执照）。
  - 若证面同时出现「法定代表人」与「主要负责人」且为不同人：以证面**主栏或加粗/表格主行**为准；仍无法判断则写入 `ambiguities`（`field_key` 用 `safetyLegalRepresentative`），选项为两个不同姓名。

**优先级**：只要危险品经营许可证（或同类安全生产许可）影像清晰可读，应**尽量**输出 `safetyIssuingAuthority` 与 `safetyLegalRepresentative`；二者在证面上通常有明确标签，漏识别视为未完成本技能的核心任务。

## 歧义（ambiguities）

若某字段存在 **2 个及以上** 合理候选（字号模糊、遮挡、**多证多主体同一键**、多证并列等），**不要**在 `form_patch` 中写入该字段，改为在 `ambiguities` 中给出：

- `field_key`：同上 camelCase 字段名
- `question_for_user`：**中性陈述**——只说明「为何无法唯一确定」（如遮挡、两种读法并存、**多张营业执照对应不同企业**），**不得**暗示应选哪一项（禁止「建议选…」「以…为准」「更可能是…」等）。
- `options`：每项含 `option_id`（简短 id）、`label`（展示文案）、`suggested_value`（用户点选后写入表单的值；**仅为数据绑定用，不代表系统推荐该值**）。各 `label` 应平行罗列事实，**不对任何候选排序或加「推荐」「优先」标签**。

**再次强调**：上文「多张证照与同一表单字段」与单证上的模糊候选**同等适用**本节的格式与禁忌；多营业执照场景下 `ambiguities` **允许且通常应为非空数组**（只要有任一上述冲突字段）。

## 回复（reply）：对话流中的结构化摘要

`reply` 与 `form_patch`（及视觉路径下的 `ambiguities`）**分工明确**：机器可消费的键值只在结构化字段里；**人类用户在左侧对话流里只读 `reply`**，因此 `reply` 必须用**固定章节 + 条目化中文**复述识别结论，便于扫读。

### 版式（更清晰）

- **不要使用 Markdown 代码围栏**（不要用成对的三个反引号包裹整段正文）。  
- 每一大节标题单独成行，使用全角【】；节与节之间**空一行**。  
- 节内列表统一用 `-`  起行；同一字段下若有子项，用缩进两格后再 `-` ，避免挤成一段长句。  
- 键名 camelCase **仅允许**出现在括号备注中，例如「发证机构（safetyIssuingAuthority）」；正文以**中文表单含义**为主。

### 必须采用的章节骨架（按顺序）

每一轮输出 `reply` 时，**依次包含下列小节**（小节标题原样使用【】；某节确实无信息时写一行「无。」占位，勿省略小节标题）：

1. **【识别概要】**
  - 1～2 句：本轮处理了哪些证照 / 用户诉求、证面或语境整体是否清晰（如「证面清晰」「右下角印章模糊」）。
2. **【已抽取字段】**
  - **与 `form_patch` 逐项对应**：每行 `- <表单中文含义>：<取值>`（需要时可加括号备注 camelCase）。  
  - 中文含义与前端表单标签一致或明显同义。  
  - **凡写入 `form_patch` 的键，在本节必须出现一行**；不要只在 `form_patch` 里给值却在 `reply` 里漏提。  
  - 日期、日期范围用可读形式（如 `2020-01-15` 或 `2020-01-15 至 2025-01-14`），与 `form_patch` 不得矛盾。  
  - 若 `form_patch` 为空：`- （本轮未向表单写入有把握字段）`。
3. **【待确认 / 歧义】**
  - **只罗列、不推荐**：与 `ambiguities` 逐条对应；每条写清——**字段（中文 + 可选 camelCase 括号）**、**为何存在多种可能**、**候选并列列出**（可用 `1.` `2.` 编号，每行一个候选，文案与 `options[].label` 对齐即可）。  
  - **禁止**：写「建议选择…」「推荐…」「更可信的是…」「以 A 为准」等任何倾向性表述；禁止比较候选优劣；禁止代用户做决定。  
  - **允许的唯一收尾句**（有歧义时，且仅一句）：中性说明操作位置，例如「请在页面右侧表单上方的黄色提示区中，对下列字段任选一项确认。」不得指向具体第几项。  
  - 若无歧义：本小节只写「无。」
4. **【未覆盖 / 说明】**
  - 列出证面或对话中明显可见但**本轮未写入 `form_patch`** 的信息类型及客观原因（遮挡、无法与规则对齐等）；若无：「无。」

### 文风与禁忌

- 全文**简体中文**；短句、列表优先。  
- 禁止在 `reply` 中嵌套 JSON、XML 或代码块。  
- 不要编造证照号码、统一社会信用代码。  
- **禁止**在 `reply` 中使用 Markdown 图片 `![...](...)` / `![](...)`，**禁止**写出任何 `http://` / `https://` 占位或示例 URL。  
- 若 `reply` 中须用文字列举证照名，**仅允许**下列四种中文全称，且**禁止**在名称后加「（如适用）」「(如适用)」等后缀：**营业执照**、**身份证人像面**、**道路危险货物运输许可证**、**危险化学品经营许可证**（与前端材料卡白名单一致；本技能**不**定义 `upload_guide` JSON，亦不加载上传引导类技能）。

### 文本对话与多图视觉的共性

- **仅文本**：【识别概要】写对用户意图的理解；【已抽取字段】只列本轮写入 `form_patch` 的项。  
- **多图视觉**：【识别概要】写证照类型与张数；【已抽取字段】**仅**列本轮实际写入 `form_patch` 的键值；若多主体冲突字段已放入 `ambiguities`，则**不得**在【已抽取字段】中重复罗列这些键的多套取值（应改在【待确认 / 歧义】展开）。

### 职责边界

本技能**只**约定 **`form_patch`**、**`ambiguities`**（视觉路径）与 **`reply`** 的版式与抽取规则。**不**负责材料清单 JSON（`upload_guide`）、上传入口说明、首次使用四卡示意；那些仅在**文本对话**里用户明确询问如何使用或缺件时，由路由层加载的其它技能处理。遵守本技能时**勿**把上传引导规则混入 `form_patch` / `ambiguities` 字段定义。

### 自检

- 每个 `form_patch` 键是否在【已抽取字段】中各有一行？  
- 【待确认 / 歧义】是否**零推荐**、仅罗列并与 `ambiguities` 一致？  
- 是否出现 **≥2 张不同主体的营业执照**？若是：凡冲突的工商单行字段是否**已从 `form_patch` 省略**并**已写入 `ambiguities`**？是否存在「reply 里列了两套企业信息却 `ambiguities` 为空」的自相矛盾？
